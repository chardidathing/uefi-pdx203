# sony xperia 1 ii (pdx203) port notes

state: builds, not yet booted on the phone. the goal of this package is the first unixnu milestone, the firmware reaches the
unixnu menu on the panel with the power and volume keys working, from an image flashed to `boot_a`. nothing of the stock
sony uefi is needed for that (see "stock inputs" for what the vendor drivers would need and where they come from).

the port follows `UniXNU/uefi-sheng` (the xiaomi pad 6s pro port unixnu ships): mu drivers only, the loader leaves the panel
scanning out and the firmware draws into that buffer, the pmic keys are read directly, the boot image ramdisk becomes a
block device. the device package is `Platforms/Sony/pdx203Pkg`, the kona bits come from `Silicon/Qualcomm/KonaPkg` like
the oneplus 8t (`kebab`) and poco f3 (`alioth`) packages this was modelled on.

## where the facts come from

| fact | value | source |
| --- | --- | --- |
| soc, panel, keys, storage, memory | sm8250, 1096x2560 splash at 0x9c000000, command mode panel, pm8150 pon keys, ufs 3.0 at 0x1d84000, dram 0x80000000.. | `ios-sweet/docs/PDX203.md`, read back on the phone by the ios-sweet shim and kernel |
| splash buffer geometry and stride | 1096x2560, 32 bpp, stride 4384 (= width x 4) | ios-sweet shim stage 1 (the red console rendered correctly) |
| command mode panel kick | pingpong 0 at 0xae71000, autorefresh bit 31 plus 1, tearcheck programmed with vsync count 123 when off | `ios-sweet/shim/display.c`, verified on the phone (pp 0 went 0 to 0x80000001, tearcheck was off) |
| pingpong offset | 0x71000 | `qcom,sde-pp-off` of the stock kona dtb (`ref/kona.dts` line 17885), the preflight checks it |
| carve-outs | every fixed `/reserved-memory` node of the stock dtb set | `ref/kona.dts`, the preflight checks all three dtbs of the set against the memory map |
| firmware regions (fd, stack, heaps, log, info blk, kernel area) | the kona uefiplat layout at 0x9bc00000..0xb4500000 | `kebab` and `alioth` memory maps (`uefiplat.cfg` of the stock qualcomm uefi), the sony `uefiplat.cfg` is not available |
| where the loader puts the kernel and ramdisk | ramdisk ends at 0xb0000000 (seen at 0xafffe000 with a tiny one), so inside the "Kernel" region 0xa0000000+0x10000000 | ios-sweet shim log on the phone |
| spmi arbiter | version 0x50010000, 512 apids, map at core+0x900, observer at 0xe600000+0x80*apid, pon apid 13, gpio1 apid 23 | `ios-sweet` kernel log (`SWEET KEYS: arb=0x50010000 apids=512 pon-apid=13 gpio-apid=23`) |
| key wiring | power = pon kpdpwr (bit 0), volume up = pon resin (bit 1), volume down = pm8150 gpio1 (0xc010 bit 0, active low) | `ios-sweet/tools/boards/pdx203.py`, keys verified in ios |
| boot image container | header v2, kernel 0x8000, ramdisk 0x2000000, tags 0x1e00000, dtb 0x1f00000, page 4096, the dtb section is the stock kona dtb set | stock `boot.img` header, the ios-sweet shim boots with the same packing |
| gic, timer | gicd 0x17a00000, gicr 0x17a60000, 19.2 mhz | `KonaPkg.dsc.inc`, matches `ref/kona.dts` and the ios-sweet shim |

## memory map

`Platforms/Sony/pdx203Pkg/Library/MemoryMapLib/MemoryMapLib.c`. ddr regions, all below 4 gb:

| region | base | size | handling |
| --- | --- | --- | --- |
| hyp, xbl aop, removed region (qsee), gap 0x85e00000, debug, last log, ramoops, cmdline | 0x80000000, 0x80700000, 0x80b00000, 0x85e00000, 0xffb00000.. | dts sizes | reservation hob, no mapping (no-map in the dts) |
| mpss efs, aop cmd db, smem | 0x80600000, 0x80860000, 0x80900000 | 1 mb, 128 kb, 2 mb | reserved, mapped uncached |
| pil carve-outs, cdsp secure heap | 0x86200000 .. 0x90d00000 | dts sizes, one row per node | reserved, mapped uncached |
| sched heap | 0x9bc00000 | 4 mb | boot services data |
| display reserved (cont_splash_region), dfps data | 0x9c000000, 0x9e300000 | 35 mb, 1 mb | reserved, write through (the splash buffer the gop draws into) |
| dbi dump | 0x9e400000 | 15 mb | mapped, no hob |
| fv region, aboot fv, uefi fd, sec heap, page tables, stack, log buffer, info blk | 0x9f800000 .. 0xa0000000 | kona uefiplat sizes, the fd is 0x9fc00000 + 3 mb | firmware's own |
| kernel | 0xa0000000 | 256 mb | reserved, mapped cached, the loader's kernel, ramdisk and device tree live here |
| dxe heap | 0xb0000000 | 69 mb | conventional memory |

`Pdx203BootMemoryDxe` adds the dram the loader's device tree lists and no carve-out or firmware region covers (up to 1 gb
below 4 gb, so 0x90d00000..0x9bc00000 and 0xb4500000..0xffb00000) as conventional memory at dxe time, and publishes the
ramdisk from `/chosen linux,initrd-start` and `-end` as a read-only block device. the dts `memory` node is empty in the
boot image, the loader fills it from the smem ram table before handing over, which is why this is done at runtime and not
in the static map.

register regions are the kona ones plus `MDSS` (0xae00000, 1 mb) and a full 1 mb `SMMU` window.

## build

the mu-silicium checkout is this repository on branch `pdx203`, cloned with submodules. the unixnu boot manager and
darwinboot are built into the firmware volume from the `UniXNU` checkout.

with the unixnu build driver (what the device repository does, `ref/firmware-pdx203.toml` is the `[firmware]` block):

```sh
cd UniXNU
export UNIXNU_UEFI=/path/to/uefi-pdx203    # the preflight needs it
./unixnu build firmware --uefi /path/to/uefi-pdx203 -D /path/to/UniXNU-pdx203 -j 24
```

the driver runs `scripts/check-pdx203.py` (copy it into the device repository's `scripts/`), initialises the submodules,
builds basetools, applies `Resources/MuPatches/Gic-Spurious.patch` to its own edk2 checkout for the build, and runs the
edk2 `build` with `FD_BASE=0x9fc00000 FD_SIZE=0x300000 FD_BLOCKS=768` and the defines of the block. the output is
`Build/pdx203Pkg/DEBUG_CLANGPDB/FV/SILICIUM_UEFI.fd` in this checkout.

standalone, the mu-silicium way (needs the pip requirements, a venv is fine, and `UNIXNU_ROOT` pointing at the `UniXNU`
checkout, default `../UniXNU`):

```sh
python3 -m venv .venv && .venv/bin/pip install -r pip-requirements.txt
UNIXNU_ROOT=/path/to/UniXNU .venv/bin/python3 build_uefi.py -d pdx203 -r DEBUG
```

this also packs `Mu-pdx203.img` with the stock header v2 layout from `Resources/Configs/pdx203.toml`. the gic patch is not
applied on this path (only the unixnu driver applies board patches), everything else is the same. stuart's external
dependencies (`Mu-Basetools`, `mu_nasm`, `onecrypto-bin`) are nuget packages, on linux that needs `mono` next to the pip
requirements (`setup_env.sh` installs it), the unixnu driver path needs neither.

build `DEBUG`. the debug log is drawn on the panel (`FrameBufferSerialPortLib`) and is the only trace of the firmware there
is on this phone, a `RELEASE` build is silent.

## boot image and flashing

the image for `boot_a` is packed with the stock sony layout, header v2, the kernel field a gzip of `BootShim` plus the
firmware volume, the stock kona dtb set (`Resources/DTBs/pdx203.dtb`, the three soc revisions back to back, the loader picks
one) in the dtb section, stock offsets, 4 kb pages:

```sh
python3 scripts/pack-pdx203-bootimg.py -o /path/to/pdx203-uefi-boot.img                 # empty ramdisk, menu only
python3 scripts/pack-pdx203-bootimg.py --ramdisk out/pdx203/payload/payload.img -o ...   # with the unixnu payload
```

`unixnu bootimg` cannot write a dtb section (it appends the dtb to the gzip stream, a header v1 container) and takes a
single dtb, not the three of the stock set, and this bootloader has only been seen to boot the stock v2 layout, so the
flashable image comes from the script. the script compiles the shim exactly like the driver and verifies the image by
unpacking it. the driver's own packing does work mechanically (`--dtb` one dtb split out of the set, 1.1 mb image with the
`[bootimg.image] header_version = 1` override of the block), it is just untested on this loader.

the first image built from this tree (empty ramdisk, `DEBUG`, fd sha256 `c0bcb3b9…34b451`, 651 kb of the 3 mb fd used):
`pdx203-uefi-boot.img`, 2158592 bytes, sha256 `c3f1cf4284a02e871caa13c1c21904afba54b174b1660b4f1bc737cf66e8d916`.

sony's bootloader has no `fastboot boot`, and slot b is blocked, so the image replaces the android boot image in slot a:

```sh
fastboot flash boot_a pdx203-uefi-boot.img
fastboot reboot
```

restore android with the stock image (`/home/charlie/source/xperia-1ii/out/boot.img`, `fastboot flash boot_a boot.img`).
`fastboot` 37 and newer are fine for `boot_a`.

## what to expect on the panel

1. the sony logo stays while the loader runs, then goes black: sec clears the splash buffer before its first log line. the
   black screen itself shows that the shim and sec ran and that autorefresh took (a frozen sony logo means the kick did
   not work or the firmware never ran).
2. white text on black from sec onwards, `Project Silicium for Sony Xperia 1 II`, the `MMU:` and `SEC:` progress lines,
   then the dxe dispatch (`BOOTMEM:` lines with the device tree address, the memory added and the initrd block device,
   `Pdx203KeyInput:` with the pon and gpio apids).
3. the unixnu menu. with an empty ramdisk unixnu runs its built-in configuration and lists removable loaders, with the
   payload volume in the ramdisk it lists the `xnu` entry. the debug log shares the buffer with the menu, the menu is drawn
   on top of it. volume up and down move, power selects. holding power for about ten seconds is the pmic hard reset, as
   always.

no uart is reachable on this phone and the mu-only firmware has no usb driver, so the panel is the log. photograph it. the
log wraps at the bottom of the screen, `gSiliciumPkgTokenSpaceGuid.PcdFrameBufferDelay` (10 ms per line, from
`SiliciumPkg.dsc.inc`) can be raised in the dsc to slow it down for a video.

if nothing appears and the logo stays: the firmware did not run or the panel kick failed. `BootShim` runs before anything
could be logged, the next step is the ios-sweet shim's stage 1 image, which prints the pingpong registers it sees.

## stock inputs (vendor drivers)

`PDX203_VENDOR_HW = 1` in the dsc adds the stock qualcomm uefi drivers (the kebab list: smem, dalsys, clocks, rpmh, spmi,
pmic, tlmm, ufs, usb, charger, tsens, buttons, ...) from `Binaries/pdx203/`. they are not in this tree and not in the
`Device-Binaries` submodule. they come out of the phone's own xbl, which carries the uefi firmware volume:

- on the phone, from the lineage recovery (adb is root there): `dd if=/dev/block/by-name/xbl_a of=/sdcard/xbl_a.img`, or
- from the sony firmware for xq-at52 (xperifirm download), the file `xbl_X-FLASH-ALL-<hex>.sin`, unpacked with `unsin`.

the ios-sweet notes say the lineage recovery is reachable over adb after killing `gvfs-gphoto2-volume-monitor` on the host.
split the image with `UEFIReader` (the silicium porting guide) or `UEFIExtract` and put the result at `Binaries/pdx203/`
(the `Device-Binaries` layout, `clean_up.py` there normalises the inf files), with the raw files `SecParti.cfg`,
`uefipil.cfg`, `QcomChargerCfg.cfg` and `BATTERY.PROVISION` under `RawFiles/`. the stock `uefiplat.cfg` from the same
image is the authority for the firmware regions of the memory map and should replace the kona assumptions in it. the
binary patches the other kona devices carry (`ButtonsDxe` power key as enter, `FeatureEnablerDxe` not restarting the tz
applet or the clocks, `UsbConfigDxe` host mode) would have to be redone on the sony binaries.

the silicium guide warns that booting windows or linux on a sony device wipes the ufs, which is the stock ufs driver
provisioning the chip against its own configuration. none of that runs in the default build, unixnu's native ufs driver
runs in xnu. do not flash a vendor-driver build with binaries from another device.

## open risks

- the arm64 header of the shim names `0x9fc00000` as text offset, the qualcomm loader is expected to load the kernel field
  at `base | text_offset`, the shim copies itself to the fd base if it lands elsewhere. the image size in the header covers
  the shim and the fd. the ios-sweet shim used text offset 0 and ran wherever it was put, this exact header has not been seen
  on sony's loader (it is what every kona device in mu-silicium ships).
- the firmware regions between 0x9bc00000 and 0xb4500000 are the kona reference layout, not sony's `uefiplat.cfg`. the
  loader's ramdisk placement (end of the "Kernel" region) was seen on the phone, the rest of the area is free dram as far
  as the stock dtb is concerned.
- the `DEBUG` build zeroes the 35 mb splash buffer with the mmu off in sec, that is some hundred milliseconds of black
  before the first line.
- the gic patch masks a spurious level interrupt the loader may leave pending (the sheng tablet had one from ipcc). on the
  standalone build path it is not applied.
- `Pdx203KeyInputDxe` only reads the arbiter. it withholds volume down when the gpio does not read back as an enabled input
  (the kernel found it configured, `mode=0 en=0x80 subtype=0x10`).
- secure boot is built out (`ENABLE_SECUREBOOT=0` in the block) so unsigned payload drivers can be loaded from the
  ramdisk later, flip it when the port is done.
- `unixnu bootimg` output (header v1, appended dtb) is untested on this loader, use the pack script.
- the stock dtb set is 1.5 mb in the dtb section, like the stock image. the loader rewrites the memory node and `/chosen`
  in the one it picks and passes it in x0, which is what `Pdx203BootMemoryDxe` reads.
